# 我的个性化 UI 设计宪章：报销申请中心范式

本文件把报销申请中心的长期偏好提炼为跨模块可复用的执行规则。它服务于采购、报销、库存、固定资产等企业工作台；业务事实、ERPNext metadata 和项目根 `AGENTS.md` 优先。

## 1. 核心目标

**严肃纯净、高信息密度、流式自适应、零误触丢失、单据链纯净。**

界面应让经办人少点一次鼠标、多看一眼关键数据、不会因误触丢一笔录入，也不会被无关控件、歧义标题或虚假的系统单据干扰。

## 2. 视觉与文案

### 2.1 纯文字、低噪与明确命名

- 默认以严肃的中文文字、颜色和共享状态标签表达含义；不新增钻石、文件、禁止、鸡雏或其他装饰性 Emoji。既有历史页面出现这些符号，不构成新代码复制许可。
- `✕` 是功能性关闭控件，可以保留，但必须配合可访问名称或明确的“关闭/取消”文字，不可作为装饰。
- 字段名只描述一个明确业务概念，禁止以斜杠将概念拼接。例如写“物料名称*”或“费用项*”，不写“物料名称 / 费用项*”。
- 展示层使用中文业务名，不直接暴露字段 API 名。字段是否存在必须核验 DocType metadata；规格正式复用 `description`，展示名为“规格”。

### 2.2 流式宽度与永不折行

- 禁止给会随中文文案变化的分段按钮、标签和主文本列设置狭窄固定像素宽度。
- 选项区采用内容优先的流式网格，例如 `grid-template-columns: auto ...`；每个选项使用 `min-width: max-content` 与 `white-space: nowrap`，让文字自然在一行内展示。
- 数值列保持紧凑且不折行；物料名称、规格、用途和备注优先获得弹性剩余空间。具体标题、正式字段和宽度区间遵循 `FIELD_CATALOG_AND_COLUMN_WIDTHS.md`。
- 响应式不是把所有内容压窄或折成多行。视口不足时让布局换行、表格横向滚动或弹窗内部滚动，但不截断关键业务语义。

### 2.3 选择与实体呈现

- 2 至 4 个互斥选项一律优先分段控件，而不是原生下拉框；状态全量可见，一次点击即可切换。
- 物料、供应商采用固定视口跟随的建议浮层：上行显示粗体代码，下行显示名称与规格，右侧为等宽参考价格；底部常驻“快捷新建”。不用原生 `datalist`。
- 已选物料、供应商和明细摘要使用 `.ashan-item-capsule` 等共享胶囊组件，保持高密度、可扫描，不堆砌冗长输入框。

## 3. 安全退出与无感草稿

### 3.1 防误触的双通道退出

- 录入、编辑、审批弹窗使用静态背景，点击遮罩不能关闭弹窗。
- 右上角必须有 `✕` 关闭入口，底部必须有“✕ 关闭”或“✕ 取消”出口。两条路径都走同一安全关闭逻辑。
- 关闭前如存在输入，先同步保存草稿；在 DOM 销毁后不得丢失已输入内容，并给出轻量提示。

### 3.2 全生命周期自动保存与恢复

自动保存覆盖全部输入生命周期：

1. 输入/键入采用约 150ms 防抖。
2. `blur`、`focusout`、换行和 Tab 切换时立即保存。
3. 新增或删除发票卡片、明细行，以及下拉选中、快捷新建回填时立即保存。
4. 页面关闭或刷新前通过 `beforeunload` 写入本地草稿。
5. 再次打开时完整恢复卡片、行、金额、税率、规格和备注，展示恢复提示并提供“重置草稿”。

空表单不得产生数据库垃圾。只有标题、物料等出现实质性内容后，才防抖静默保存服务器草稿。保存成功后，只以小体积 JSON 局部刷新主列表和 KPI，不整页刷新、不抢焦点、不打断输入。

## 4. 报销发票的精确联锁

| 发票类型 | 发票号码 | 税率 | 计算与提示 |
| --- | --- | --- | --- |
| 专用发票 | 必填，显示红色 `*` | 默认 13%，允许编辑 | 实时计算税额和价税合计 |
| 普通发票 | 必填，显示红色 `*` | 允许编辑，例如 1%、3%、6% | 实时计算税额和价税合计 |
| 无发票 | 禁用；提示“无发票（系统自动编号）”；不显示 `*` | 强制为 0 且禁用 | 不允许以其他类型的默认税率误算 |

这不是视觉层的小把戏：提交和服务端保存必须使用相同规则复核，不能只靠前端禁用控件。

## 5. 草稿与单据链边界

### 5.1 草稿优先且不制造噪音

- 列表稳定排序为：`ORDER BY (CASE WHEN rr.docstatus = 0 THEN 0 ELSE 1 END) ASC, rr.posting_date DESC, rr.name DESC`。
- 草稿始终置顶，使用琥珀左侧提示条与“待提交草稿”文字标签；状态不可只凭颜色理解，也不加装饰性 Emoji。
- 用户直接关闭空白新建框时，既不创建服务器单据，也不污染主列表。

### 5.2 现金报销只走必要闭环

- 现金报销只生成 Purchase Invoice（PI）、Purchase Receipt（PR）、Reimbursement Request（RR）三单闭环；不得为了凑流程额外创建 Purchase Order（PO）。
- 明细包含库存品时，按业务事实自动入库和过账；服务端回填 PI、PR、RR 的关联关系，并校验公司、角色、库存与提交状态。
- 前端可提供进度可视化，但不拥有最终财务事实。Document 生命周期、权限校验和库存/金额复核必须由服务端执行。

## 6. 实现与验收清单

1. 是否使用 `ashan_ui_kit.css` 的组件和令牌，且未新增 `style=`？
2. 所有用户文案是否无装饰性 Emoji、无歧义斜杠标题，并且字段名已由 metadata 核验？
3. 分段文字和高语义列是否在常见视口自然单行，不因固定窄宽度折行？
4. 弹窗遮罩是否不能误关，右上角与底部两条关闭通道是否都会保存草稿？
5. 是否实测输入、失焦、Tab、结构增删、刷新、重开恢复、重置草稿，以及空表单不建单？
6. 是否实测专票、普票、无票的号码、星号、税率、税额和价税合计联锁？
7. 是否实测草稿置顶、局部刷新不抢焦点，以及 PI—PR—RR 关联和库存品路径？
8. 是否通过共享 UI 治理检查、真实浏览器控制台零新增报错和关键截图验收？

## 7. 速记

> 视觉：纯文字、去装饰、标题准、单行舒展、分段直达；
> 交互：防误触、双退出、失焦存、换行保、动态联锁；
> 逻辑：空不生、有即感、草稿顶、局部更、链纯净。
