# 动态业务边界与财务严肃性

本资料记录 Ashan 项目的第一设计原则：让每一张表、每一个金额和每一个状态只表达它应表达的业务事实，并随真实当期数据动态变化。

## 1. 事实优先，绝不硬编码

- 人数、工资、分类、基数、月份、税额、凭证和汇总均从当期数据与有效配置计算。
- 示例中的人数、金额和期间仅是样例，不能成为条件判断、显示文案或导出模板中的固定常量。
- 无值应保持空白或明确的零值语义；不得私自填入“正常”“系统核定”“一口价”等业务结论。
- 计算、导出、页面 KPI 和封账拦截必须基于同一份期间快照或同一套服务端计算结果，避免前后不一致。

## 2. 集合纯净：谁应出现在何处

| 范围 | 正确数据集合 | 禁止混入 |
| --- | --- | --- |
| 全员母表 | 当期所有在册员工 | 仅以车间发薪决定是否在册 |
| 车间外部实发表 | 当期真实车间出勤且由车间实发的员工 | 外籍工、高管等非车间出勤人员，即使已录入固定薪资 |
| 个税申报与综合结算 | 全体当期在册、依法应参算人员 | 只取车间实发集合 |
| 社保/公积金当期操作表 | 当期实际缴费人员 | 以表格过滤错误改变全量汇总 |

对类别、人数、零工资与特殊人员的显示必须实时统计。例如任务副标题采用“系统计薪 N 人｜外部实发计薪 M 人｜0 工资 Z 人”，而不是固定数字。

## 3. 用工类别与税务边界

分类以劳动/用工性质而不是五险一金标签为准：正式工、退休返聘/达龄留用、临时/零工、其他类型（含外籍或管理特殊类型）和本月离职人员。各类数量、零工资数量和参算范围动态计算。

- 临时工/零工不进入累计预扣税表，税额为零。
- 返聘、退休返聘、其他返聘和外籍人员应依法进入累计预扣范围。
- 外籍工的直接录入税后薪资与七项专项附加扣除必须参与完整的反推和企业总成本计算。
- 个税基本减除费用按申报周期实际存在的历史记录月份累计，禁止按自然月机械倍乘。
- 个税的七项专项附加扣除必须端到端贯通：子女教育、继续教育、大病医疗、住房贷款利息、住房租金、赡养老人、3 岁以下婴幼儿照护。

## 4. 工资月与缴费月：两只时钟

令工资核算月为 `P`：

- 薪资计算、当月例外、快照、重算都以 `P` 为唯一业务边界。
- 社保/公积金的实际缴费与凭证所属期为 `P + 1`；页面、文件名、导出标题和校验文案必须明示“实际缴费所属期”。
- 公积金季度自动规则以实际缴费月判断。实际缴费月为 1/4/7/10 才命中季度自动缴纳，不能拿 `P` 直接判断。
- 参缴优先级：本月例外（仅 `P` 有效） > 员工长期策略 > 公司自动规则。固定缴纳与一次性强制缴纳不是同一种策略；后者须限定当月并留审计痕迹。
- 法定排除类型（返聘、临时/零工、外籍、实习等）无论策略或基数为何，均不参与相应缴费。

## 5. 凭证、封账与追溯

- 上传的 Excel、PDF、ZIP 等原始凭证以二进制原样归档，不得用系统二次生成文件覆盖。
- ZIP 自动解压后，只向用户交付内部真正的凭证源文件；统一命名为 `{期间月份}_{企业名称}_{凭证类型}_原始凭证.{ext}`。
- 封账前实时检查：底册、车间实发导入、社保申报核验、公积金凭证核验等当前期间的前置项。缺一项即返回清单式拦截，不得默许封账。
- 封账后全局只读；反审核/解锁必须记录原因、操作者和时间，并可审计回放。

## 6. 计算与展示检查清单

在提交薪酬、税务、社保或凭证功能前，逐项验证：

1. 输入集合与输出集合的边界是否书面明确？
2. 所有期间计算是否以 `P` 和 `P + 1` 正确区分？
3. 特殊人员、零工资、离职人员和外籍工是否走到正确支路？
4. 所有总计是否从全量服务端数据计算，而非从可见表格行相加？
5. 原件是否无损、可下载且命名规范？
6. 状态转换、封账和解锁是否都留下可审计证据？
