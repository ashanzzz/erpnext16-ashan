# 交易工作台生命周期规范：报销、月结入库与自办电汇

本规范用于报销申请中心、月结入库补录、自办电汇及后续同类工作台。目标是共享严肃、低噪、高密度的 UI，同时让每个动作准确匹配真实业务状态；不因页面长得相似，就把编辑、删除和草稿做成同一件事。

## 1. 先区分三种对象

| 对象 | 用户可以做什么 | 不可混淆的边界 |
| --- | --- | --- |
| 本地未提交录入 | 增加、移除、恢复行；关闭后恢复 | 它不是数据库单据，不能叫“删除报销单” |
| 服务器草稿 | 原位保存、原位编辑、删除草稿、提交 | 空表单不建单；同一草稿不能每次编辑都重建新单据链 |
| 已提交业务链 | 查看、按权限发起作废/重开/解锁 | 已影响库存、税务、付款或审计的单据不应被“保存修改”隐式删除重建 |

按钮文案必须说清对象与后果：本地用“移除此行”，草稿用“删除草稿”，已提交链路用“发起作废重开”或对应审批动作。不得用一个泛化的“删除”掩盖级联取消、库存回滚或凭证影响。

## 2. 当前代码基线：可复用之处

三个工作台都已经具备一部分共同基础：高信息密度的 Picker 主表、创建弹窗、物料行的增删、金额实时计算、公司范围服务端校验以及 `ashan-*` 视觉组件。报销中心还具备：

- 服务器草稿按 `docstatus = 0` 置顶排序，且主表/明细表均标示草稿；
- 静态背景弹窗、右上角 `✕`、底部关闭入口与显式“暂存草稿”；
- 现金报销的 RR、PI、PR 三单边界，且不创建 PO；
- 编辑详情和删除前确认的基础能力。

月结入库与自办电汇当前是“确认即创建并提交”类型：月结生成 PO 加 PR；电汇生成 PO、按库存情况生成 PR、再生成 PI，并可能建立 RR。它们适合共享录单组件和本地恢复机制，但当前没有同等的服务器草稿、编辑或删除服务端生命周期。

## 3. 当前不一致与改造方向

### 3.1 报销中心

1. 草稿现为手动点击“暂存草稿”，关闭弹窗会直接销毁 DOM；尚未覆盖输入、防抖、失焦、行增删与页面离开的自动恢复。
2. “保存修改并过账”在已有报销单时会先调用整单级联删除，再新建链路。这会改变单据标识，可能丢失关联、附件或审计上下文；该行为不应隐藏在“保存修改”里。
3. 级联删除的服务端会取消后物理删除 RR、PI、PR。它应改为按状态、角色、公司和关联影响分层处理：草稿可删除；已提交单据默认走可审计的取消/作废重开流程，物理删除只能是受控维护动作。
4. 草稿状态、过滤按钮、标题、删除按钮和成功提示仍带装饰性 Emoji；新的用户可见文本应改为纯中文状态和动作。

### 3.2 月结入库与自办电汇

1. 创建弹窗没有明确设置静态背景、右上角安全关闭、底部关闭和本地草稿恢复的完整契约；用户在输入中误关或刷新时可能丢失内容。
2. 行删除当前是立即移除。对已经填写物料、数量、单价或备注的行，应提供短暂撤销或轻确认；空行可直接移除。
3. 两页没有服务器草稿、原位编辑或链路删除接口。不要为了“看起来和报销一致”就在提交前生成正式 PO、PR、PI、RR；优先保存本地可恢复状态。只有用户明确需要跨设备或跨日继续录入时，再设计一个独立的根草稿与版本控制。
4. 电汇的两项发票类型应使用分段控件，不应使用原生下拉框；物料选择应由输入后 `change` 查询升级为视口跟随的双行建议浮层与快捷新建。

### 3.3 共同视觉整改

- 移除用户界面的装饰性 Emoji；功能性 `✕` 仅用于关闭/移除控件。
- 使用“规格”而不是“规格型号”；使用“备注”或“用途说明”而不是“用途/备注”。字段实现仍需复用 `description` 与已核验的备注字段。
- 现有 `.ashan-col-w*` 固定列宽仅可用于序号、操作、金额等安全短列。物料名称、规格、备注等应使用最小宽度加弹性剩余空间；不将长中文压窄或折成多行。
- 月结、电汇弹窗可以继续复用 `.ashan-smart-modal` 的流式视口约束，但新布局必须复用共享 CSS 令牌，禁止在 HTML 新增 `style=`。

## 4. 统一交互契约

### 4.1 创建与恢复

1. 打开新建框时仅建立本地状态，不写数据库。
2. 用户输入标题、供应商、发票号码或有效物料行等实质内容后，约 150ms 防抖写入本地草稿；失焦、Tab、行增删、选择回填、关闭和 `beforeunload` 同步保存。
3. 重开时完整恢复表头、卡片、行、金额、税率、规格和备注，展示“已恢复未完成录入”并提供“重置草稿”。
4. 只有业务明确需要服务器草稿时，才在实质输入后静默创建**唯一根草稿**，并以局部 JSON 更新主表。不得为每次输入或每张发票建立新的正式业务链。

### 4.2 编辑

- `docstatus = 0`：编辑同一根草稿，使用版本或 modified 时间防止并发覆盖；提交时由服务端重新校验。
- `docstatus = 1`：界面默认只读。若业务允许纠正，使用“发起作废重开”并要求原因，确认层列出 RR、PI、PR、PO 等受影响单据、库存和付款影响；操作员只能申请，管理员审批。
- 主表中点击单号应优先打开查看/管理弹窗；不要让用户猜一支铅笔图标是修改草稿还是会撤销已提交链路。

### 4.3 删除与取消

- 本地空行：可直接移除；已有输入行：可撤销或轻确认。
- 服务器草稿：在确认后删除根草稿及其草稿附件/临时明细，服务端验证模块角色与公司范围。
- 已提交单据：默认不能物理删除。执行取消、作废或重开时保留审计原因、操作者、时间和原链路；服务端先检查是否已付款、已核销、已有下游单据或库存回滚限制。
- 所有变更型 RPC 使用 POST；前端按钮不是权限边界。`ignore_permissions=True` 只能放在已完成角色、公司、状态和关联检查后的最终必要写入处。

## 5. 按工作台执行

| 工作台 | 推荐草稿策略 | 编辑/删除策略 | 提交后的标准单据边界 |
| --- | --- | --- | --- |
| 报销申请 | 本地自动恢复；需要服务端草稿时仅 RR 根草稿 | 草稿原位编辑；已提交按作废重开，不隐式删后新建 | RR + PI + PR，不创建 PO |
| 月结入库 | 默认本地自动恢复；跨设备需求才创建独立根草稿 | 已提交 PO/PR 用 ERPNext 标准取消/更正，不从 Picker 伪编辑 | PO + PR |
| 自办电汇 | 默认本地自动恢复；跨设备需求才创建独立根草稿 | 已提交 PO/PR/PI/RR 走状态化更正，禁止无提示重建 | PO + 可选 PR + PI + 可选 RR |

## 6. 交付验收

1. 三个工作台的创建弹窗均为静态背景，均有右上角 `✕` 与底部关闭出口，且两条路径都保全本地草稿。
2. 实测输入、失焦、Tab、增加行、删除有内容行、刷新和重开恢复；空表单不会生成服务器记录。
3. 仅报销服务器草稿按 `docstatus = 0` 置顶；月结、电汇在未设计服务器草稿前不伪造草稿列表。
4. 实测草稿编辑不会新建重复业务链；已提交更正会显示影响清单、原因与权限边界，且保留审计。
5. 实测专票、普票、无票联锁；月结/电汇两项互斥选择使用分段控件。
6. 表头不含装饰性 Emoji、无歧义斜杠标题；规格、物料名称、备注按语义获得合理弹性列宽。
7. 运行 UI 样式治理检查，并用真实浏览器测试三页的创建、关闭、恢复、查看、删除/作废和控制台零新增报错。
