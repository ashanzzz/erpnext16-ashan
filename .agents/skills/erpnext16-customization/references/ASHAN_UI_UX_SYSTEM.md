# Ashan UI 设计语言与交互系统

目标：桌面端 ERP 页面在高信息密度下依然清晰、快速、可恢复，并保持 Frappe Desk 的原生习惯。

## 1. 系统入口与基本令牌

- 所有静态视觉优先复用 `ashan_cn_procurement/public/css/ashan_ui_kit.css` 的 `ashan-*` 类；公共 JS 能力位于 `public/js/ashan_ui_kit.js` 的 `window.AshanUI`。
- 新代码禁止增加 HTML `style=`。动态视觉状态使用 class、`data-*` 或现有组件；确实无法表达的例外必须先获用户批准并在同一变更中说明。
- 常用令牌：深蓝灰（信息主层）、蓝（操作/可点击）、绿（完成/实发）、琥珀（草稿/提醒）、红（锁定/危险），8px 级间距、6/8px 圆角、克制阴影。
- 金额用 `fmtMoney(value)` 或 `AshanUI.formatMoney(value)`；金额单元格带 `.ashan-money-cell` / `.qifu-money-cell`，等宽数字、右对齐、不换行。

## 2. 组件优先级

| 场景 | 优先复用 | 要点 |
| --- | --- | --- |
| 卡片 | `.ashan-card` | 等高、核心指标优先、不要纯装饰卡片堆叠 |
| 状态 | `.ashan-status-badge` | 草稿/成功/弱提示有明确颜色且不只依赖颜色 |
| 提示 | `.ashan-callout`、`.ashan-inline-notice` | 明确动作、影响与恢复方式 |
| 操作 | `.ashan-btn-primary/success/danger/outline` | 一个明确主操作，其余退居次级 |
| 自动保存 | `AshanUI.createSaveIndicator` | 固定宽度，状态切换不挤动相邻按钮 |
| 账期 | `AshanUI.renderPeriodSelector` | 上/下月、本月、明确年月；防止未封账跳月 |
| 实体切换 | `AshanUI.renderEntityTabs` | 切换可见、保留上下文 |
| 选择建议 | `.ashan-suggest-*` / `.picker-suggest-*` | 双行信息 + 价格 + 常驻快速新建 |
| 弹窗 | `.ashan-smart-modal` + `frappe.ui.Dialog` | 静态背景、明确关闭、草稿保护 |

## 3. 页面结构与响应式

- 顶部 KPI 和筛选栏采用自适应网格，如 `repeat(auto-fit, minmax(200px, 1fr))`，让大屏充分利用宽度、小屏自然换行。
- 弹窗使用流式约束：`width: min(94vw, 1400px); max-width: 95vw; margin: 1.25rem auto;`；内容区限制到视口内并滚动，标题与操作区常驻。
- 固定标识列保持安全最小宽度；名称/说明列弹性占余量；金额、税率、数量、单价使用等宽数字并禁止折行。
- 控制栏中的年月、公司、按钮应保持同一高度（当前工作台标准为 36px）和基线对齐。
- Loading、空态、错误态应在内容区明确呈现，不能用沉默空白代替错误；错误消息说明“发生了什么、影响什么、下一步如何处理”。

## 4. 宽表、表头与冻结

- 表头采用**单层复合表头**：一个 `th` 内上方放逻辑分组小胶囊（约 9px/600），下方放主标题（约 12px/700）；不要通过复杂 `colspan`/`rowspan` 叠层造成缩放和冻结漂移。
- 标识列的冻结语义：序号 `.qifu-col-sticky-1`，工号 `.qifu-col-sticky-2`，姓名 `.qifu-col-sticky-3`；最后一列冻结列有轻微右投影；底部合计用 `.qifu-col-sticky-foot`。
- 宽表高度按当前视口动态计算，让横向滚动条贴近用户可见的底沿；避免页面外层长纵向滚动导致“看不到姓名和横向滑块”。
- 建立顶部辅助横向滚动条并双向同步。表头和主体都启用 `AshanUI.enableMousewheelHorizontalScroll`：纵向滚轮在有横向溢出时转换为横向滚动。
- 表格不因只显示当期操作行而影响总计；服务端必须仍计算完整集合。

## 5. 导航、选项与选择器

- Tab 默认与激活状态均保持 600 字重并预留边界；激活只改颜色，不用 `translateY` 造成布局抖动。
- 选项不超过四个时，使用分段标签或胶囊单选；`select` 隐藏上下文、需要两步点击，仅适合选项较多的场景。
- 物料/供应商不能使用原生 `datalist`。建议下拉应使用固定视口定位并跟随输入框：上方代码（蓝色粗体）、下方名称+规格（灰色）、右侧参考价格（绿色等宽），底部常驻“新建物料/供应商”。
- 一级侧边栏：文字区负责“展开/收起并跳转分类工作台”，右侧箭头仅负责展开/收起；二级单据只做 SPA 路由切换，不折叠父级。二级无图标、缩进表达层级。

### 5.1 已确认的高效紧凑控件风格

当 2～4 个互斥模式各自需要一句解释时，采用“紧凑双行选择卡”。它是普通分段控件的说明增强版，不是通用大卡片：简单的“是/否”“待处理/已完成”仍使用普通胶囊选项。

- **字体层级**：组标题使用约 `12px / 600`；选项主标题使用约 `12px / 700`；单句说明使用约 `10.5px / 1.45` 和灰蓝色；边缘快捷入口的当前值使用约 `11px / 650`，日期和金额继续使用等宽数字。默认沿用系统字体栈，不为局部控件额外加载字体。
- **细边框语言**：默认采用 `1px` 中性浅灰边框、浅灰底和 `6px` 圆角；悬浮只轻微转为浅蓝；激活态使用蓝色细边框、浅蓝底和约 `2px` 的低透明度聚焦环。阴影仅用于建立一层轻微浮起感，不使用厚重描边、强渐变或大面积高饱和色块。
- **紧凑布局**：双选项优先使用 `repeat(2, minmax(0, 1fr))`，间距约 `8px`，卡内间距约 `9px 10px`。标题与说明左对齐并保持两级阅读顺序；说明尽量为一句，不把控件撑成宣传卡片。
- **动态显隐**：默认模式只呈现模式说明；只有用户选择需要额外参数的模式时，才显示对应日期、期间或其他字段。隐藏字段不占空白，说明区域保留最小高度，切换时避免底部按钮上下跳动。
- **可访问性**：激活状态同时通过边框、背景和文字层级表达，并设置 `aria-pressed`；键盘焦点使用清晰的 `:focus-visible`，不能只依赖颜色区分状态。
- **令牌复用**：实现时从 `ashan_ui_kit.css` 读取 `--ashan-color-slate-*`、`--ashan-color-blue-*` 与 `--ashan-radius-*`，允许安全回退值，但不得在不同页面复制出多套近似颜色。

这种风格也适用于侧边栏中的低频工作上下文入口：上层显示短标签与“修改”，下层显示当前公司、期间或日期。入口宽度随侧栏流动，长公司名称省略但通过 `title` / `aria-label` 保留完整信息。

账户姓名、邮箱、头像和个人资料菜单属于身份导航，必须保持 Frappe 原生点击行为。公司、期间、业务日期等业务上下文应使用独立入口，放在身份区上方或邻近位置；不得拦截、改写或复用原生用户菜单来承载业务设置。

弹窗采用“字段标签 → 双行模式选择 → 一句动态说明 → 必要时出现依赖字段”的顺序。主操作保持唯一且稳定，次操作为关闭；默认模式不显示无用输入框，使字体、边框和留白共同服务于快速判断。

## 6. 弹窗、草稿与防误触

- 所有录入、编辑、审批弹窗使用静态背景，禁止点击遮罩丢失工作。
- 同时提供右上角醒目的关闭按钮和底部“取消/关闭”按钮。离开前若有输入内容，在销毁 DOM 前同步保存草稿并提示用户。
- 自动保存覆盖：输入/键入（约 150ms 防抖）、失焦/切换、增加或删除结构、下拉选择/新建回填，以及 `beforeunload`。
- 重开弹窗时检测有效草稿、完整恢复卡片/行/金额/备注，并提供显眼的恢复提示和“重置草稿”。
- 快捷键支持 Ctrl/Cmd+S 保存草稿、Esc 走安全关闭逻辑；不绕过未保存检测。

## 7. 单证与财务可读性

- 中国企业标准单证/打印采用清晰的网格、区分外框和内框；导出表头明确所属期、公司和数据范围。
- 财务页面同屏优先呈现：税前应发、税后实发、个人代扣、单位承担和企业综合总用工成本。
- AI 匹配或异常判断必须显示依据、候选及可撤销的确认操作；不可把建议直接渲染成不可解释的最终财务事实。

## 8. UI 交付检查

1. 是否复用了公共样式/JS，而非复制颜色和间距字面量？
2. 是否新增了 `style=`？若没有，运行 `python scripts/verify_ui_style_governance.py`。
3. 宽表、冻结列、横向滚动、弹窗和草稿路径是否由 Playwright 实测？
4. 小屏、分屏和宽屏下是否没有外部裁切或错误固定宽度？
5. 控制台是否为零新增报错，金额/状态/空态是否清楚可读？

## 9. 文案、图标与字段来源纪律

- 默认使用严肃、简洁、可打印的中文文本和视觉语义；不为“活泼”而引入 Emoji。尤其不得新增 `🐣` 一类拟人化/卖萌符号，也不以 Emoji 代替状态名称、按钮动作或错误原因。用户明确提出且业务语义清晰时才可例外。
- 保留既有页面中的历史符号不等于可以在新页面复制；改造旧页面时逐步用文本、状态标签、颜色和图标系统替代装饰性符号，不做无关的大范围视觉重写。
- 标题必须表达业务事实，不用开发术语污染用户界面。例如使用“规格”“单据明细”“业务模式”“实际缴费所属期”，而不是字段名或模糊的“信息”“数据”。
- 字段名不是由中文标签反推。实现前读取 `FIELD_CATALOG_AND_COLUMN_WIDTHS.md`，再核验目标 DocType metadata；字段不存在时先定位业务来源，而不是猜一个 `custom_*` 名称。

## 10. 数据来源色彩与按钮生命周期

| 来源/状态 | 默认视觉语义 | 交互要求 |
| --- | --- | --- |
| 系统自动推导、全局联动、只读结果 | 浅灰 `#f1f5f9`、灰蓝文本 | 显示“自动获取/系统推导”依据；不可伪装成人工录入 |
| 人工长期策略或显式例外 | 白底、高对比文本 | 允许编辑，明确标识是个体独立配置 |
| 补缴、跨期差异、待办草稿 | 琥珀色系 | 说明为何需关注，保留人工确认与恢复路径 |
| 删除、金额不符、法定拦截 | 红色系 + 明确文字 | 危险操作要求确认，不能仅靠颜色传达 |
| 已导入、核验一致、实发完成 | 绿色系 + 明确文字 | 就地展示结果、凭证入口或下一步 |

按钮应随数据生命周期在**同一入口原位演进**，而不是堆叠上传、删除、下载等并列按钮：

1. 未上传/待处理：显示唯一直接的“上传/导入/开始核验”动作。
2. 已上传/已就绪：原按钮切换为“删除已上传…”等受确认的危险动作，并在邻近位置显示凭证下载标签。
3. 删除完成：清空关联核验与就绪状态，按钮即时还原为上传入口；封账资格同步重新计算。

空表单不得生成服务器单据；出现实质输入后，才以防抖静默保存为草稿，并局部刷新列表与 KPI。草稿按 `docstatus = 0` 置顶，使用文字化琥珀状态标签，不使用卖萌 Emoji。

### 状态筛选的点标语义

- 在“待处理 / 已完成 / 全部”这类互斥筛选中，用户明确认可用 `🟡` 标识待办、用 `🟢` 标识已完成；点标必须紧邻完整中文状态文字，不能单独承担含义。
- “全部 / 汇总 / 不限”是中性聚合条件，使用纯文字（如“全部申请单据”），**不得使用 `🌐`**。地球表达地域、网络或全球范围，不表达“全部”。
- 这是一项明确的业务状态例外，不扩展为页面装饰：其余操作、标题、提示和空态仍遵循无装饰性 Emoji 的默认规则。

## 11. 列宽的语义化分配

容器保持流式响应，列宽则按信息密度分级；具体标题、字段和宽度区间见 `FIELD_CATALOG_AND_COLUMN_WIDTHS.md`。

- 序号、勾选、状态、短编码、日期、单位、税率、数量和金额保持紧凑的安全宽度。
- 物料名称、规格（`description`）、单据明细和备注是高语义文本，必须优先获得可伸缩的剩余空间；不能被金额列或操作列挤到不可读。
- 备注/规格可限制合理的单元格行数或以悬浮完整内容辅助阅读，但默认不把正文截断成无法判断的省略号。
- 宽表的列宽规则与 Excel 打印列宽分开维护：Web 追求实时操作，Excel 追求黑白审计和纸张边界。

## 12. 个性化报销中心模式

- 用户文案以纯中文、业务事实和明确动作表达。默认移除装饰性 Emoji（例如钻石、文件、禁止类符号）；右上角 `✕` 可保留为功能明确的关闭控件。字段标题不能用斜杠把不同概念混在一起：业务上是物料就写“物料名称”，是费用就写“费用项”。
- 分段控件和高频文本列不设狭窄固定像素宽度。以内容宽度和可用视口共同决定布局，使用 `grid-template-columns: auto ...`、`min-width: max-content` 与 `white-space: nowrap` 等规则，保证中文选项自然单行展示；整体容器仍遵循流式响应。
- 报销发票类型只有 2 至 4 项时使用分段控件。专用发票与普通发票都要求发票号码，均显示必填星号；专票税率默认 13% 但可编辑，普票税率同样可编辑并实时计算税额与价税合计。仅“无发票”禁用发票号码和税率，将税率设为 0，展示“无发票（系统自动编号）”，并隐藏必填星号。
- 草稿列表按 `docstatus = 0` 优先、再按日期与名称倒序的稳定顺序呈现；草稿使用琥珀左侧提示和“待提交草稿”文本标签。空弹窗不写入服务器；出现标题、物料等实质内容后才防抖静默建草稿，并以局部 JSON 刷新列表/KPI，禁止整页刷新、抢占焦点或生成垃圾单据。
- 现金报销只建立业务所需的 Purchase Invoice、Purchase Receipt 与 Reimbursement Request 三单闭环，不强行创建 Purchase Order。库存品由服务端按实际规则入库并回填关联；链路完整性、库存与权限校验不能只依赖前端。
- 物料、供应商的输入仍使用固定视口跟随的双行建议浮层和常驻“快捷新建”；已选实体和明细优先使用 `.ashan-item-capsule`，而非大面积冗长文本框。

完整的个人取舍、实现边界和验收清单见 `PERSONALIZED_UI_CHARTER.md`。

## 13. 交易工作台的生命周期一致性

报销、月结入库、电汇等工作台应共享视觉和防误触语言，但不能把“草稿、编辑、删除”机械做成同一套按钮。先判定该操作作用于本地未提交内容、服务器草稿，还是已提交且已影响库存/财务的单据链；然后使用对应的动作、权限、确认和审计强度。

- 本地明细行的移除可使用功能性 `✕`，但有实质输入时应给撤销机会或轻确认；绝不能把它伪装成已提交单据的“删除”。
- 服务器草稿编辑应原位更新同一根单据，空表单不建单；列表草稿置顶并以文字化琥珀状态展示。
- 已提交链路不允许在“保存修改”中暗中物理删除再重建。需要改正时明确使用“发起作废重开/解锁申请”等审计动作，并在确认层列出受影响单据、库存/付款影响和原因要求。
- 即时过账的月结、电汇创建器可先采用本地可恢复草稿；只有用户有暂停跨设备录入的真实需求时，才设计服务端草稿，且不应预先生成正式 PO、PR、PI、RR 等业务链。

交易工作台的现状基线、统一契约和改造优先级见 `TRANSACTION_PICKER_LIFECYCLE.md`。

## 14. Ashan 模块统一工作台

Ashan 自定义模块统一的是工作台外壳、设计令牌、基础组件、交互契约与性能策略；不统一各模块的法定计算、数据集合、权限状态机或单据链。新页面优先复用共享 CSS、`AshanUI` 与可配置的页面骨架，而不是复制其他页面的大段 HTML、事件和样式。

- 首屏只获取必要的筛选、KPI 与列表摘要；详情、附件、关联链路按用户点击再取，搜索防抖且局部刷新，不做整页重绘和无意义轮询。
- 统一组件必须能正确初始化、重复进入页面和销毁，避免 Frappe SPA 路由后重复绑定事件或保留无效定时器。
- 为统一而新增的实现应保持轻量，优先沿用 Frappe、共享 CSS/JS 与现有 API；不得仅为“框架感”再引入整套前端框架或一次加载全部模块代码。
- 每次只迁移一个可验收功能区或一个工作台，保持数据接口与业务结果不变；完成真实浏览器验收后再推进下一页。

分层架构、性能边界和迁移顺序见 `ASHAN_WORKBENCH_ARCHITECTURE.md`。
