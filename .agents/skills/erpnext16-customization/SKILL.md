# ERPNext16 定制百科与 Ashan 风格

在 ERPNext / Frappe 16 的定制、重构、审查或验收任务中使用本技能。目标是把业务事实、可用性、权限和可验证交付同时做好，而不是只生成看起来合理的代码。

## 使用边界

- 本技能面向 ERPNext 16 / Frappe 16 的**自定义应用**。默认不修改 `apps/frappe` 或 `apps/erpnext` 核心。
- 当前仓库 `AGENTS.md`、站点配置、已安装版本和业务数据优先于本技能；冲突时，先说明冲突并以实际环境为准。
- 本技能不携带任何真实账号、密钥、工资或个人资料。需要凭据时只读取已获授权的环境配置，不写入代码或文档。
- 涉及财务、库存、薪酬、税务、凭证、提交/取消、权限或迁移时，先读取相关参考资料并做实机验证；不能依据记忆猜测 API 或状态。
- 新增用户可见文案、状态和操作控件默认不用装饰性 Emoji，尤其禁止引入 `🐣` 一类拟人化/卖萌符号。仅当用户明确指定且该符号具有业务语义时才可使用；颜色与清晰文字才是默认状态表达。
- 用户可见字段标题必须是严谨、完整的中文业务名称，禁止以斜杠拼接两个不同概念（例如不写“物料名称 / 费用项”）；功能性关闭符号 `✕` 可作为明确的退出控件，不属于装饰性 Emoji。
- 常用列标题和字段名必须从字段目录或当前 DocType metadata 获取；物料规格的唯一正式字段是 `description`（界面名“规格”），不能自行杜撰 `custom_spec_model`、`custom_guige_xinghao` 等替代字段。

## 首次判断

1. 确认任务类型：业务规则、后端/API、UI/交互、权限、数据导入导出、迁移，或验收。
2. 读取项目根 `AGENTS.md` 与本项目业务规则；再读取下方“按需资料”中的最小集合。
3. 读取当前 custom app 实现和对应 Frappe/ERPNext v16 Controller；官方资料只用于核对，不能替代运行中的源码。
4. 如任务会变更数据或发布，先给出影响范围、权限边界与验收方法；未经授权不扩大写入范围。

## 不可违背的工作原则

### 业务与财务

- 数据集按权责边界保持纯净：母表/全员汇算、车间实发、法定申报和综合成本各自以正确集合动态计算，绝不把特殊人员或零工资人员错误混入。
- 所有人数、金额、期间、人员类别、税费基数和凭证状态都来自当期事实和配置，禁止用演示数字或固定月份作为逻辑。
- 原始凭证以原二进制无损归档；压缩包仅提取应交付的源文件，命名统一且可追溯。
- 最终封账由实时前置条件拦截；封账后只读，解锁必须有原因与审计记录。
- 工资核算月与实际社保/公积金缴费月是两只时钟；缴费月为核算月加一，季度规则和凭证校验必须基于缴费月判断。
- 祺富（天津市祺富汽车配件有限公司）与吉众（天津吉众科技有限公司）薪酬体系绝对隔离：两家企业的考勤逻辑、工时计算公式、薪资表单、个税反推与点钞配钞彻底不同，所有薪酬表单与工作台绝对不通用！侧边栏严格划分为【祺富人事薪酬与用工】与【吉众人事薪酬与用工】，严禁通用化、混用或强行统一。

### 架构与安全

- 定制先放在 custom app；使用 Document、Controller、Hooks、标准工作流与 Frappe API，而不是直改核心或绕过生命周期。
- Frappe Desk Page 是缓存式 SPA：首次 `on_page_load` 与再次显示 `on_page_show` 必须分工明确。工作台实例应按 wrapper 幂等保存和恢复；页面内 DOM 查询、事件绑定与刷新必须限制在该页面的 body/wrapper，不能依赖全局重复 ID。
- 每个自定义模块只保留“管理员 / 操作员”一对业务角色；菜单不可见性从不是安全边界。所有服务端读、写、导入、导出、锁定和审批都须检查角色及公司范围。
- 所有改变数据的 RPC 使用 `POST`，先校验输入、权限、公司、状态及源 Document；`ignore_permissions=True` 只能出现在这些强校验之后的最终写入。
- 财务或库存建议可以由 AI 生成，但最终保存前必须由服务端重新加载并复核 ERPNext Document。

### 体验与界面

- 复用 `ashan_ui_kit.css` 和 `AshanUI` 公共能力；新代码不得增加 HTML `style=`，动态状态用 class 或 `data-*` 表达。
- 高信息密度不等于拥挤：使用统一卡片、状态标签、金额等宽右对齐、单层复合表头、冻结标识列和可见的总计。
- 宽表必须让表头/主体可横向滚动，并支持顶部同步滚动条与鼠标滚轮转横向；外层页面不应要求用户为找横向滚动条而进行无意义的纵向滚动。
- 弹窗背景不得误触关闭，必须有右上角关闭和底部取消/关闭；用户已输入内容要自动暂存。选项不超过四个时优先分段胶囊选项而不是下拉框。
- 需要解释差异的 2～4 个互斥模式采用紧凑双行选择卡：上层短标题、下层一句说明、细边框与轻量激活反馈；简单短选项仍使用普通分段胶囊，避免把所有选择器都做成大卡片。
- 账户姓名、邮箱和个人资料入口保持 Frappe 原生职责；公司、期间、业务日期等工作上下文使用独立的紧凑入口，禁止劫持身份入口的点击行为。
- 录入交互覆盖输入、防抖、失焦、结构变化和离开页面的自动保存与草稿恢复；状态提示应稳定、不引起布局跳动。
- 分段控件和文本列按内容与视口流式伸缩，文字保持单行；不得为图省事写狭窄固定宽度而让中文折行。报销的专票、普票、无票联锁、草稿置顶与单据链规则遵循个性化 UI 宪章。
- 表格常规数值度量列（库存量、金额、单价、单重、数量等）必须以纯粹的“数字 + 法定主计量单位”等宽靠右排版（`tabular-nums`），严禁在每一行滥用带背景和边框的卡片/药丸（Badge）包裹；胶囊徽标严格仅用于互斥的核心单据状态。
- 交易工作台的“编辑、删除、草稿”不能按页面外观复制：先识别该页创建的是本地录入、服务器草稿，还是已提交的财务/库存单据链；操作文案、权限、确认和审计强度必须与实际生命周期匹配。
- Ashan 自定义模块统一采用轻量“工作台框架 + 业务适配层”：共享页面骨架、组件、交互契约和性能纪律；各模块仅适配自己的数据、权限、状态机和单据链，绝不把财务/库存逻辑硬统一。

## 实施流程

1. **定位事实源**：按任务读取业务规则、现有实现、标准 Controller 与最少的官方资料。
2. **设计最小变更**：明确数据所有者、参与集合、状态转移、角色/公司校验、失败提示及恢复路径。
3. **实现**：遵循 PEP 8、函数 docstring、确定排序；前端保持闭包作用域、使用共享组件和 `fmtMoney`/`AshanUI.formatMoney`；先按字段目录使用正式字段及语义化列宽。
4. **静态检查**：Python 复杂逻辑先做语法检查；前端运行 UI 内联样式治理检查。
5. **热同步与迁移**：按照项目脚本执行；“脚本显示完成”不等于迁移成功，必须以实际 migrate 退出结果为准。
6. **浏览器验收**：使用 Playwright 真实进入 Desk，走关键点击和弹窗路径，检查控制台、网络、权限和截图；没有证据不声称通过。
7. **交付说明**：说明改变了什么、为何符合业务边界、验证证据和仍需用户决定的事项。

## 何时停止并请求确认

- 需要新增/删除生产数据、调整权限给更多用户、改变法定计算规则、删除原始凭证、覆盖历史迁移或推送到远程仓库。
- 当前实际规则与本技能冲突，且无法从源码/配置判断哪个应优先。
- 找不到当前版本的官方资料或实际 Controller，且该推断会影响财务、税务、权限或数据完整性。

## 维护本技能

当用户确认新的长期风格、业务纪律或验收经验时，编辑相应 `references/` 文件并更新 `references/CHANGELOG.md`。不把瞬时任务细节、生产数据或秘密写入知识包。
