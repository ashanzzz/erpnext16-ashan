# Architecture and security governance

## Runtime source of truth

The app currently has several historical layers. For maintenance, use this order:

1. `hooks.py` for active Frappe hooks and globally loaded assets.
2. Page JSON/JS and actual `frappe.call` targets for active Desk workbenches.
3. `services/authorization_service.py` and `services/permission_query_service.py` for server-side authorization patterns.
4. Domain services such as `reimbursement/service.py` for reusable business rules.
5. Package README files as documentation only. They must be updated when code changes.

The former `fixtures/custom_html_block.*` mission-control frontend is retired and removed. It is not an active routing, navigation, or permission source and must not be restored.

## Authorization model

### Company scope

All custom company-scoped endpoints must call `assert_company_access(company)` once a concrete company is known. Context endpoints may call `get_allowed_companies()` and return only that set.

### Standard ERPNext documents

For Material Request, Purchase Order, Purchase Receipt, Purchase Invoice, Stock Entry, Payment Entry, Supplier, Item and similar standard records:

- read through Frappe permission-aware APIs, or filter SQL result identities through `permission_query_service`;
- create/submit/cancel/delete through standard document lifecycle permissions;
- do not use `ignore_permissions=True` as a workbench shortcut.

### Custom manager operations

Monthly Invoice Closing is a custom control record. Lock/unlock is authorized by an explicit manager-role gate and Company scope. Its internal save may use `ignore_permissions=True` because the service-level role gate is the product authorization boundary. This exception is narrow and documented in code.

## Purchase Invoice rules

All Purchase Invoice entry paths share these rules:

- active invoice numbers are unique system-wide in this app;
- procurement monthly closing protection applies to both `posting_date` and `bill_date`;
- tax-invoice matching must be refreshed when a special workflow changes submitted invoice metadata;
- base-currency values must use `conversion_rate`; transaction-currency amounts must not be copied directly into base fields;
- `outstanding_amount` is left to ERPNext's normal accounting lifecycle rather than overwritten during tax validation.

The self-service wire-transfer “complete invoice” action is an exceptional submitted-document metadata patch. Before patching it explicitly runs the normal closing and invoice-number validators, checks standard write permission, then re-runs tax-invoice matching.

## Reimbursement implementation map

There are two cooperating layers rather than one exclusive file:

- `reimbursement/service.py` contains reusable source-selection, reservation and validation logic.
- `reimbursement/api.py` contains thin RPC wrappers around that domain layer.
- `services/reimbursement_picker_service.py` is the multi-invoice Desk workbench adapter and orchestration layer used by `page/reimbursement_picker`.

A workbench adapter may orchestrate Purchase Receipt / Purchase Invoice / Payment Entry creation, but standard permissions remain mandatory.

Cascade deletion is restricted to Purchase Invoices and Purchase Receipts whose `custom_biz_mode` proves they were generated by the cash-reimbursement flow. Existing source procurement documents are preserved.

## Wire-transfer lifecycle

The current `wire-transfer-picker` UI intentionally exposes two document states:

- `draft`
- `completed`

Receipt, issue, invoice-completion and payment progress are separate facts/linked documents. Old four-state lifecycle labels are not part of the current filter contract and must not be reintroduced in one layer only.

## Payroll bootstrap

`get_payroll_workbench_context()` is called before a company is selected. It therefore checks the payroll role first with `assert_payroll_access("read")`, then returns only `get_allowed_companies()`.

Every operation after company selection must bind the authorization check to that company.
