## 一、 业务背景与全厂人员四大分类公理 (Employee Archetypes)

祺富机械每月由车间/统计提交一份车间工资 Excel（如《祺富工资2026.10.xlsx》）。该表格由**“上方主工资表”**（车间出勤与计件明细）与**“下方补贴表”**（职位补贴、房车补）两部分组成。全厂人员绝非单一工种，系统及后续 AI **必须严格按以下 4 类模型进行识别与分流处理**：

### 1. 计件考勤操作工族 (Piece-Rate Workshop Workers)
* **代表人员**：王永、曹付云、刘风魁、贾翠丽、李金刚、万晓莉等（共 19 人，含 5 名退休返聘工）。
* **Excel 源表位置**：上方主工资表（通常为编号 3 及之后）。
* **计薪特征**：
  - 拥有完整的工时与计件列：作业天数、作业小时、天工资、小时工资、全勤费、加班小时、加班费、国勤天数、达标率、达标工资、扣除项。
  - Excel 原件公式为 `=ROUND(天工资+小时工资+全勤+达标+加班+国勤-扣除, 0)`。
* **个税与社保规则**：
  - 正式工全额缴纳社保（最低基数或核定基数）与公积金；
  - 退休返聘工（李淑华、张引弟、刘丽艳、林伯新、贾建丽）在母表标记为“返聘工”，免缴社保公积金，但**依法全额参与个人所得税累计预扣**；
  - 全员以其实际到手金额为目标，通过 7 级累计预扣闭式反推税前应发工资。
* **24列发放表导出规则**：
  - 第 P 列（考勤绩效工资合计）写入 Excel 联动计算公式：`=F{row}+G{row}+H{row}+J{row}+L{row}+N{row}-O{row}`。

---

### 2. 定额技术/管理反推族 (Fixed-Net Reverse Calculation Workers)
* **代表人员**：
  - **孟祥山 (QF0006)**：管理部负责人，统管财务、采购与环安。
  - **翟风杰 (QF0004)**：生产部设备机修与电工技术骨干。
* **Excel 源表位置**：上方主工资表最前端（编号 1、2 行）。
* **计薪特征**：
  - **不通过考勤工时/计件联动算薪**！
  - 孟祥山：有出勤天数记录，但无天工资、无小时工资、无达标工资，车间实发直接给定定额数值（例如 2026-10 为 `8,752.00` 元，2026-09 为 `8,732.00` 元）；
  - 翟风杰：有出勤与全勤加班记录，但其车间底薪为固定定额 `6,500.00` 元（原件公式为 `=ROUND(6500+K4, 0)`），并在下方补贴表中领取职位补贴 `2,000.00` 元，两项合计实发 `8,500.00` 元。
* **个税与社保规则**：
  - 属于企业在册正式工，全额缴纳社保与住房公积金（孟祥山公积金个人扣 1,000 元）；
  - 档案发薪模式设定为 **`税后动态工资（税后倒推）`**；
  - 系统以其实际定额实发金额为基准，扣减五险一金个人部分后，自动通过国家标准 7 级累计预扣反推税前应发工资与个税。
* **24列发放表导出规则（核心避坑）**：
  - **严禁对其第 P 列套用考勤加减公式**！因为其没有天工资/小时工资，套用公式会导致计算结果为 0 或 100，造成实发被归零。
  - **规则**：检测到无考勤明细（`day_salary == 0 and hour_salary == 0 and target_salary == 0`）时，第 P 列直接填入其实际车间实发定额数值（孟祥山 8,752，翟风杰 6,500），与补贴列（Q、R）累加后等于实发合计（V 列）。

### 3. 纯补贴管理/临时工族 (Allowance-Only Non-Tax Temporary Workers)
* **代表人员**：**徐凤云 / 徐经理 (QF0068)**（管理部主管）。
* **Excel 源表位置**：**上方主表完全无行次**；仅出现在下方补贴表（第 47 行，以别名 `徐经理` 出现，职位补贴 `3,600.00` 元）。
* **计薪特征**：
  - 上方车间作业天数与工时均为 0，车间实发为 0；
  - 纯粹发放职位补贴 3,600.00 元，当月实发合计 3,600.00 元。
* **个税与社保规则**：
  - 档案标记为 **`临时工 / 不税动态工资`**；
  - 不缴纳社保与公积金；
  - 依据中国财税与企业薪酬规约，临时工不进入正式工综合所得累计预扣申报台账，个税金额固定为 0；
  - 税后实发 = 税前应发 = 3,600.00 元。
* **24列发放表导出规则（核心避坑）**：
  - **严禁因作业天数/工时为 0 或工号未以 "A" 开头将其过滤**！
  - 规则：只要在册且当月 `net_salary > 0`，必须完整进入 24 列实发表，第 P 列填空或 0，第 Q 列（职位补贴）填 3,600，第 V 列（实发合计）为 3,600，并自动生成 36 张百元钞票的现金点钞明细。

## 二、 端到端解析与自动化处理管道 (Processing Pipeline)

任何后续 AI 在处理薪酬导入与结算时，必须确保执行以下 5 阶段管道流转：

```
[原始 Excel 文件] 
       │
       ▼
【阶段 1: 语义双表解析】 
  ├─ 自动定位主考勤表与下方补贴表
  └─ 别名系统 (Alias Engine) 智能归一：
       "徐经理" -> QF0068 徐凤云
       "刘海峰" -> QF0003 刘海锋
       "张引娣" -> QF0016 张引弟
       "王杰"   -> QF0004 翟风杰
       "米庆菊" -> QF0021 米清菊
       │
       ▼
【阶段 2: 实发守恒聚合】
  net_salary = round(workshop_net + post_allowance + house_car_allowance, 2)
  只要 net_salary > 0，全员保留，绝不误杀纯补贴或管理人员
       │
       ▼
【阶段 3: 税后反推引擎 (Net-to-Gross Engine)】
  ├─ 临时工/零工: 税前 = 税后, 个税 = 0
  └─ 正式工/返聘工: 
       目标净发 - 社保扣款 - 公积金扣款 -> 7级累计预扣闭式反推 -> 税前工资 + 当月个税
       验算: money_round(税前 - 社保 - 公积金 - 个税) == money_round(目标实发) (分毫不差)
       │
       ▼
【阶段 4: 24 列台账自适应呈现与导出】
  ├─ 计件普通工: 第 P 列输出考勤公式 =F+G+H+J+L+N-O
  └─ 定额/反推工: 第 P 列直接输出定额数值 (孟祥山 8752, 翟风杰 6500)
       最终实发列 V = ROUND(T + U, 0)，联动现金点钞助手 (100/50/10/5/1元)
       │
       ▼
【阶段 5: 会计连续账期状态机】
  前一月 (如 2026-09) 封账锁定后 -> 下一月 (2026-10) 自动开账；严禁测试脚本向已封账历史月重新写入
```

## 三、 四大历史高危陷阱与硬红线 (AI Guardrails)

后续接手的 AI 必须在代码与操作中严格守住以下红线：

### 陷阱 1：考勤公式清零陷阱 (Formula Flattening Bug)
* **表现**：导出的 Excel 中，孟祥山实发变 0 元，翟风杰实发变 2,100 元。
* **根因**：盲目为所有人套用考勤加减公式 `=F+G+H+J+L+N-O`，由于管理/机修定额人员无天工资/小时工资，公式求和得出 0，导致覆盖了真实薪酬。
* **铁律**：导出时必须判断 `has_att_components`，若无工时计件明细，第 P 列必须输出真实数值 `r.get("workshop_net")`。

### 陷阱 2：出勤与工号误杀过滤陷阱 (Zero-Attendance Exclusion Bug)
* **表现**：徐凤云（徐经理）上传后在 24 列发放表里消失，总人数少 1 人。
* **根因**：底层过滤规则写了 `if work_hours == 0 and attendance_days == 0 and not str(employee_no).startswith("A"): continue`，徐凤云工号为 `QF0068` 且工时为 0，被错误误杀。
* **铁律**：发放表过滤唯一合法条件是：`work_hours == 0 and attendance_days == 0 and net_salary <= 0`。只要有实发到手金额，任何在册人员绝不允许过滤。

### 陷阱 3：测试脚本击穿封账状态陷阱 (Billing Period Reversion Bug)
* **表现**：用户反馈“每次 AI 修改代码后，我都必须重新核定确认 9 月份”。
* **根因**：自动化测试脚本（如 Playwright 质检）在验证上传接口时，盲目使用 9 月份的 Excel 跑测试，触发了 `upload_and_import_qifu_salary` 中的 `settle_doc.status = "草稿"; settle_doc.locked = 0`，将已封账的 9 月打回草稿。系统风控检测到 9 月未封账，强行把 10 月锁死并要求重新封账 9 月。
* **铁律**：自动化测试脚本**绝对禁止向处于已封账状态的历史账期执行真实写入或重新导入**！测试文件上传必须使用当前开放的草稿账期（如 2026-10）或在隔离沙箱中执行。

### 陷阱 4：临时工进入申报台账陷阱 (Temporary Worker Tax Trap)
* **表现**：个税台账人数与实际个税申报表不符。
* **铁律**：临时工（如徐凤云）在系统内按规定只领劳务/补贴，不参加个税累计预扣申报，当月个税必须为 0，个税台账只纳入正式工和返聘工。
