# 阿山工控系统字段命名与中文术语标准化词典 (Field Naming Taxonomy)
**文档版本**: v1.0.0  
**适用范围**: ERPNext 16 (`ashan_cn_procurement`)、所有自定义 Page、DocType、报表与 API 报文  
**管理目标**: 彻底根除“同符号多中文名”与“同概念多称谓”的认知分裂，确立**底层 Schema 字段 ➔ 顶层中文标准术语**的双向一对一法定映射。

---

## 一、 核心铁律与治理背景

### 1. 字段增设与 AI 编码治理三原则 (AI Governance & Look-Up-First)
当 AI、工程师或自动化工具需要为系统添加一个表头、报表列或底层字段时，必须严格遵循以下三步治理流水线：
1. **查表先行 (Look-Up-First)**：
   - 严禁凭空发明新的英文变量名或中文展示名！
   - 必须首先检索本文档（`FIELD_NAMING_TAXONOMY.md`）及底层 DocType Schema，查明系统是否已有表达相同或相近业务概念的字段。
2. **有则复用 (Direct Reuse)**：
   - 只要当前已有字段能够满足业务需求（哪怕字段名略偏抽象，如用 `posting_date` 表达主业务发生日），**必须无条件直接复用已有英文字段与对应的法定中文名**，严禁制造同义重叠字段。
3. **严格 1-to-1 法定双向绑定 (Strict 1:1 Variable-to-Label Binding)**：
   - 若确需新增字段，英文字段名（代码变量名 / Schema fieldname）一旦确立，**必须在本文档中登记唯一的法定中文名称**。
   - **一个英文变量名全系统有且仅能对应唯一的法定中文名**！绝对禁止同一个英文变量（如 `posting_date`）在 A 页面叫“申请日期”、在 B 页面叫“过账日期”、在 C 页面叫“记账日期”等分裂行为。

---

### 2. 表头列宽设计的“动静分离”架构法则 (Fixed vs Fluid Column Strategy)
在工控数据表格的物理呈现上，列宽绝不能随意设置或默认平分，必须严格遵循“动静分离”法则：
1. **固定长度列 (Fixed Columns / 强类型像素锁死 - 必须定宽 px)**：
   - **适用对象**：字符长度固定、格式高度可预期的字段；
   - **物理表现**：必须使用 CSS 原子类锁死绝对宽度（`width: Npx !important; min-width: Npx !important; max-width: Npx !important;`），杜绝因屏幕尺寸或邻近内容变动而产生晃动或被压缩；
   - **标准定宽数值**：
     - `√ 多选框`：`40px`
     - `# 序号`：`44px`
     - `所属公司`：`72px` (精准容纳 2 汉字胶囊徽章)
     - `单据编号`：`135px` (精准容纳 15~18 位等宽单据流水号)
     - `单据日期`：`108px` (精准容纳 10 位 `YYYY-MM-DD` 日期)
     - `单据状态`：`88px` (精准容纳 2~4 汉字工业胶囊)
     - `物料项数`：`75px`
     - `计量单位`：`56px`
     - `制单人`：`90px` (精准容纳 2~4 汉字真实中文姓名)
     - `操作`：`80~100px`
2. **动态/长文本列 (Fluid / Elastic Columns / 空间弹性吸收器 - 弹性 auto / 百分比)**：
   - **适用对象**：字符长度动态不固定、长短悬殊的变长文本（如 `单据明细`、`物料名称`、`业务备注`）；
   - **物理表现**：
     - 每一张表格**有且仅有一列**声明为空间弹性吸收列（`.col-w-fluid`，`width: auto !important; min-width: 220px !important;`）；
     - 该列作为全表的**“负压海绵”**，在宽屏下吃掉所有的多余空白空间，在窄屏下以 `min-width: 220px` 保证基本可读性；
     - **严禁**对长文本列滥用 `width: 100% !important`（会导致其暴力挤爆定宽列）；
     - **严禁**让所有列均分百分比（会导致固定长度的日期、公司被严重挤压变形）。

### 3. 历史乱象与治理背景
在过去的系统迭代中，由于多人协作与不同阶段的代码引入，存在严重的术语混淆现象：
1. **同符号多中文名（严重混淆）**：
   - 底层字段 `posting_date`：在物料申请叫“申请日期”、在采购订单叫“订单日期”、在收货入库叫“过账日期”、在月结补录叫“入库日期”、在自办电汇叫“单据日期”、在发票列表叫“开票/过账日期”；
   - 用户在系统内切换页面时，产生极大的心智负担，无法确定这到底是“入库的时间”、“发票的时间”还是“录入系统的时间”。
2. **同概念多称谓（随意见文生义）**：
   - 尚未结清付款的金额（`outstanding_amount`）：在采购执行叫“待付余额”、在入库开票叫“未付余额”、在发票核销叫“当前未付余额”、在合同台账叫“待结款金额”、在报销申请叫“待付金额”；
   - 制作单据的系统责任人（`owner`）：在不同页面被随意写成“制单人”、“录单人”、“经手人”、“经手/申请人”、“创建人”。

### 标准化硬红线 (Non-Negotiables)
- **底层 Schema 与顶层 UI 必须一对一双向绑定**：每个底层标准字段，在 UI 表头与表单 Label 上必须有且仅有一个法定的中文术语；
- **杜绝复合模糊称呼**：严禁出现“开票/过账日期”、“经手/申请人”这类斜杠复合词，职责与概念必须清晰拆分；
- **面向业务的一致性**：业务操作人员在使用不同模块时，面对相同的概念看到的是完全一致的中文词汇。

> **原则**：业务单据的主日期统一确立为**“单据日期”**；税务发票自身的票面日期称为**“开票日期”**；物流交付要求称为**“期望交付日”**。彻底废止“过账日期”这一生硬的直译外来词！

| :--- | :--- | :--- | :--- |
| `posting_date` / `transaction_date` | **单据日期** | <s>过账日期</s>、<s>入库日期</s>、<s>订单日期</s>、<s>业务日期</s>、<s>记账日期</s>、<s>开票/过账日期</s> | **通用单据主日期**：单据正式生效、入账或发生业务的基准日期（格式 `YYYY-MM-DD`）。 |
| `bill_date` | **开票日期** | <s>发票日期</s>、<s>税票日期</s>、<s>账单日期</s> | **税务专有**：纸质/电子增值税发票票面打印的开具日期。 |
