# ERPNext 16 报销：未付款采购发票导入设计

状态：已实现，现场验收待用户确认  
范围：`ashan_cn_procurement` 的 `Reimbursement Request` 与 `Reimbursement Invoice Item`

## 1. 参考实现复盘（8888 / ERPNext 15）

已实际检查 8888 的 ERPNext 15.93。该功能不是自定义 App，而是：

- `Reimbursement Request` Client Script（约 3.9 万字符）；
- API 类型的 Server Script `reimbursement_helper`（约 2.6 万字符）。

它提供了一个成熟的两步导入体验：

1. 草稿报销单点击“获取未付发票”。
2. 发票弹窗按采购发票展示：发票号、日期、类型、供应商、物料摘要、待付金额；支持全文搜索、排序、整行勾选、全选、清空和已选金额合计。
3. 可整票导入，也可进入“选择未付发票明细”弹窗，逐行勾选后导入。
4. 导入后在报销明细中保留物料、规格、数量、单位、单价、金额、备注、来源采购发票和来源发票行。
5. 已提交报销单可刷新来源发票的付款状态；付款由快捷入口发起。

参考实现的候选条件是：`Purchase Invoice.docstatus = 1` 且 `outstanding_amount > 0`，并按公司过滤。对于部分付款发票，它按“发票行金额 / 发票总额 × 发票未付额”折算可导入金额。

### 不直接复制的部分

参考实现虽是 Frappe Python Server Script，但使用了原始 SQL、`db_set` 和缓存键做草稿锁定；也没有作为 App 源码随版本维护。它会带来三个风险：

- 缓存锁不是可审计、可恢复的正式占用；两个草稿可在边界情况下竞争同一来源行。
- 原始 SQL 绕开了 v16 的权限查询习惯和 Document 生命周期。
- 付款状态从来源发票余额反推，不能说明哪一笔 Payment Entry 实际对应哪一张报销单。

因此，v16 保留其用户体验，但以 App 服务、Document 生命周期和正式占用记录实现。

## 2. v16 产品目标

用户在一张报销申请草稿中，选择“已提交且尚有未付余额”的采购发票或其明细行，将经过服务器复核的来源快照导入报销明细。草稿占用来源行；提交时再次验证；付款继续使用 ERPNext 标准 Payment Entry。

本功能不创建 GL Entry、不修改 Purchase Invoice 的付款状态、不自动提交 Payment Entry。

## 3. 目标界面

### 报销申请表单

填写公司后显示表单自定义按钮：`获取未付款发票`。它不使用会被 Frappe 工具栏刷新覆盖的 secondary action，因此保存草稿、导入后刷新或重新打开单据时均会保留。主表保留公司、报销日期、标题、报销人和只读合计；明细表显示已导入来源快照。

新建报销申请不要求先保存：用户可先在浏览器中选择并预览服务器核验后的明细；首次保存时才建立正式 Draft 占用。已保存草稿则在确认导入时立即建立占用。

### 已选实现方式：一个单一原生 Dialog

参考 8888 的宽表格弹窗，使用 `frappe.ui.Dialog`，不新建页面、不引入 Vue。筛选条件与结果列表始终在同一个窗口中，筛选输入后即时刷新列表，不再出现“先筛选、再选择发票”的第二层弹窗。

- 固定当前公司、已提交、尚有未付余额；
- 顶部筛选：发票号、发票日期起止、发票类型、供应商、物料名、待付金额起止；
- 顶部有“发票选单 / 明细选单”模式切换，默认发票选单，并在当前浏览器记住用户最后一次选择；
- 下方列表随模式显示发票分组或单行物料明细，均使用同一组筛选条件；两种模式都先显示采购发票的“单据日期”，再显示发票信息；
- 提供刷新、全选当前结果、清空选择和已选待付合计，金额显示为 `1,234.00元`；
- 点击整行即可选中，无需只点复选框；发票模式中的部分已选状态会明确显示；
- 两种模式共用同一组“来源采购发票明细行”选择；主按钮统一为“确认导入”。

### 单据列表显示

| 列 | 说明 |
| --- | --- |
| 选择 | 勾选框；点击整行切换 |
| 单据日期 | `posting_date` |
| 发票号 | `bill_no`，并显示来源单据号 |
| 发票日期 | `bill_date` |
| 供应商 | 采购发票供应商 |
| 物料摘要 | 最多三项，超出显示数量 |
| 可报销金额 | 按当前未付余额折算后的金额 |

筛选与列表共享同一个状态；底部即时显示“已选项数、可导入合计”。确认导入后由服务器返回“导入 X 行、可报销合计”的结果提示。

导入完成后自动关闭弹窗，表单的“获取未付款发票”按钮保留；再次打开时，刚导入的来源会从发票模式和明细模式排除。新建报销单若存在 Frappe 默认的空白占位明细行，会在写入来源明细前自动移除，首条导入明细始终从第 1 行开始。

## 4. 金额与候选规则

### 候选采购发票

服务器只返回同时满足以下条件的单据：

1. `docstatus = 1`；
2. `outstanding_amount > 0`；
3. 公司等于当前报销申请公司；
4. 当前用户对该 Purchase Invoice 具有读取权限；
5. 来源行未被其他有效报销申请占用。

候选查询先用 `frappe.get_list("Purchase Invoice", ...)` 得到权限过滤后的发票，再在这批名称范围内读取明细。不能让浏览器提交的发票号直接成为查询范围的权限替代。

### 部分付款

若发票仍有未付余额但不是全额未付，明细的可报销金额按来源明细的含税金额占发票总来源金额的比例分摊到 `outstanding_amount`，并以两位小数处理尾差，确保一张发票的明细可报销金额之和严格等于其未付余额。分摊始终先对整张发票的全部来源行计算，再筛选用户选中的子集；绝不因已导入或当前只选择部分明细而把剩余未付额重新分配给剩余行。

含税金额优先取本项目已存在的 `custom_gross_amount`；不存在时由标准明细金额和税额计算。`description` 是唯一规格来源，类型为 Data、标签为“规格”。

v1 不支持手工拆分同一来源发票行。需要部分报销时，应在来源付款/发票层处理后重新导入；这样占用与审计最清楚。

## 5. 草稿占用与重复处理

新增 App 自定义 DocType：`Reimbursement Source Reservation`（不直接展示给普通用户）。这是唯一新增的技术对象，用它替代不可靠的缓存锁。

核心字段：

- `source_purchase_invoice`、`source_purchase_invoice_item`；
- `reimbursement_request`；
- `reserved_amount`、`status`（Draft / Submitted / Released）；
- `active_source_key`（唯一索引）：有效占用时等于来源发票行名，释放后清空；
- 来源金额快照与创建/释放时间。

规则：

1. 确认导入时，服务器在同一事务中重新核验候选行、写入报销子表并建立 Draft 占用。
2. 其他草稿和其他报销单不再看见该来源行；当前草稿的已导入行也从两个选单中排除，不能重复添加。
3. 删除明细、清空明细、删除草稿时，服务器同步释放对应 Draft 占用。
4. 提交报销单时，Draft 占用转为 Submitted；取消报销单时释放。
5. 提交前再次读取 Purchase Invoice 与来源行，检查提交状态、公司、剩余未付额、占用归属和金额快照。任一不一致则阻止提交并说明冲突。

这比 8888 的缓存草稿锁可审计，也能处理浏览器关闭、缓存过期和草稿长期存在。

唯一索引使两个用户同时确认同一来源行时，数据库只能接受其中一个占用；另一个请求得到明确的“该明细刚被其他报销草稿占用”提示。整个操作使用正常 `Document.insert()` / `save()`，不自行提交事务。

## 6. 服务器与前端边界

### App 服务

代码归属：`ashan_cn_procurement/reimbursement/`。

| 操作 | 入口 | 规则 |
| --- | --- | --- |
| 查询候选发票 | 单一 Dialog 的只读 whitelist 方法 | 使用 `get_list` 的公司、状态和未付额过滤，保留当前用户的记录权限 |
| 读取候选明细 | 只读 whitelist 方法 | 服务器计算可报销金额、排除已占用来源行；客户端不能自行计算最终金额 |
| 确认导入 | POST whitelist 方法 | 重新核验后通过 `Document.save()` 写草稿与占用 |
| 删除/重建占用 | 报销单 Controller 生命周期 | 服务器以子表为准同步 Reservation |
| 提交/取消 | 报销单 Controller 生命周期 | 重新核验、转换或释放占用 |

API 不接受浏览器传入的金额作为事实；浏览器只传递被选择的来源发票或来源行标识。

### 前端

`public/js/reimbursement_request.js` 只负责按钮、单一 Dialog、客户端筛选状态和结果提示。它不承担金额复核、占用或付款状态写入。

## 7. 单据与付款状态

当前 `Reimbursement Request` 需要改为可提交单据，才能明确区分 Draft、Submitted、Cancelled，并让占用随生命周期变化。

付款阶段不自动创建或提交 Payment Entry。后续如加入“创建付款凭证”，必须使用 ERPNext 标准 Payment Entry 流程并将对应凭证显式关联到报销申请；在此之前，报销单仅显示来源采购发票的实时未付状态，不能把它当作本报销单的精确付款归因。
